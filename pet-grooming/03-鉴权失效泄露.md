## Overview

- Pet Grooming Billing Software (SourceCodester, author mayuri_k), version 1.0 (current public download, 2026-11), "protects" its admin pages with an auth include that sends a `Location` redirect header **without terminating the script**. Every protected page therefore continues to execute all of its database queries and renders its complete output — into the body of the HTTP 302 response. An unauthenticated client that simply does not follow the redirect receives the full administrator page, including live business data. Additionally, several admin endpoints (`admin/operation/*`, fetch/AJAX handlers) have no session check at all, allowing unauthenticated state-changing operations.

## Root Cause

- The central session gate, `assets/constants/check-login.php`, redirects without `exit`:

```php
// assets/constants/check-login.php:4-13
if (isset($_SESSION['logged']) && $_SESSION['logged'] == "1" && $_SESSION['role'] == "admin") {
  $myemail = $_SESSION['email'];
  $myvataor = $_SESSION['avator'];
} else {
  header("location:../");
}
// <- no exit; execution continues
```

- Every admin page that includes `include/head.php` or `include/header.php` inherits this gate (`admin/include/head.php:4`, `admin/include/header.php:6`). In PHP, `header()` does not stop execution: after the `Location: ../` header is queued, the page's own code keeps running — all `SELECT` queries execute, all rows render — and the entire HTML output is sent as the body of the 302 response.

- A second class bypasses the gate entirely: the following files perform queries or write operations with **no session check whatsoever** (they do not include `check-login.php` at all): `admin/fetch_product_details.php`, `admin/get_barcode_data.php`, `admin/fetch_unit_price.php`, `admin/load_products.php`, `admin/barcode.php`, `admin/update_customer.php`, `admin/add_category.php`, `admin/add_tax.php`, `admin/customer.php`, `admin/product.php`, `admin/order.php`, `admin/order1.php`, `admin/stock1.php`, `admin/election.php`, `admin/pramamed.php`, `admin/change.php`, `admin/operation/paid.php`. Of these, `admin/operation/paid.php` performs **writes** (INSERT into `tbl_installement`, UPDATE of `tbl_invoice` totals) reachable without any session — unauthenticated financial-record tampering, demonstrated below.

## Impact

- Anyone who can reach the deployment can read protected admin pages (with live customer and order data) and invoke state-changing admin operations without an account. The leaked 302 body is a complete rendered page: in the demo deployment it contains the customer dropdown populated from the database with all seeded customer names, invoice form fields, and internal navigation. On a real deployment the same channel exposes real customer PII and business records to unauthenticated users, and the write endpoints allow creating installment records and altering invoice paid/due amounts without authentication.

- Response (verbatim, redirect NOT followed):

Host: 127.0.0.1:8149
Content-Type: application/x-www-form-urlencoded

inv_no=POC-UNAUTH-2&insta_amt=100&due_total=50&ptype=1&paid_amt=200&id=1

- Response (verbatim):

```
{"status":"success","message":"Customer saved successfully"}
```

  and a direct database check confirms the new installment row created by the unauthenticated request (`tbl_installement`: id 6, inv_no `POC-UNAUTH-2`, 100, 50). Repeating with `id=1&due_total=999` also rewrote invoice #1's `due_total` to 999 through the file's parameterized-but-unauthenticated UPDATE path (invoice totals restored afterwards).

## Evidence

No screenshot is required — the leak is a header/body property of the raw HTTP response, which browsers hide by following the redirect (same evidence precedent as file-download findings).

## Suggested repair

1. **Terminate after the auth redirect:** change `assets/constants/check-login.php` to `header("location:../"); exit;` — one token stops the entire 302-body leak class across every protected page.
2. **Add the gate to the unprotected handlers:** require `check-login.php` (with the fixed, exiting version) at the top of all `admin/operation/*` and fetch/AJAX endpoints — especially `operation/paid.php`, which mutates financial tables.
3. **Defense in depth:** move `admin/operation/` out of the document root or deny direct access via server config; use POST-only, token-protected handlers for state changes.
4. **Regression test:** assert that unauthenticated requests to every admin file return an empty 302 body (or 403), not rendered content.
