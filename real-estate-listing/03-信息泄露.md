## Overview

- Real Estate Property Listing App (Using PHP and MySQL), version 1.0 (current public download, 2026-11), returns raw `PDOException` messages to unauthenticated visitors from its public inquiry endpoint `/submit_inquiry.php`. Any input that makes the INSERT fail — a `property_id` that does not exist, or a value longer than a column's width — is answered with the verbatim SQLSTATE error, leaking the database name, table names, the foreign-key constraint name with its referenced table/column, and per-column length restrictions. This is exactly the schema intelligence an attacker needs to aim SQL-injection or constraint-abuse follow-ups at the deployment.

## Details

- Vulnerable file: `/submit_inquiry.php`
- Affected version: 1.0 (current public download, 2026-11)
- The exception handler concatenates the raw driver message into the JSON response:

```php
// submit_inquiry.php:23-30
try {
    $stmt = $pdo->prepare("INSERT INTO inquiries (property_id, customer_name, customer_email, customer_phone, message) VALUES (?, ?, ?, ?, ?)");
    $stmt->execute([$property_id, $customer_name, $customer_email, $customer_phone, $message]);

    echo json_encode(['success' => true, 'message' => 'Inquiry submitted successfully!']);
} catch (PDOException $e) {
    echo json_encode(['success' => false, 'message' => 'Database error: ' . $e->getMessage()]);
}
```

- The endpoint is public (`submit_inquiry.php:2` includes only `config.php`; no authentication or rate limit), and both `property_id` (:5) and the other fields (:6-9) are attacker-controlled, so an unauthenticated visitor can trigger schema-revealing errors at will.

## Description

- Any visitor can submit a manipulated inquiry form and receive internal database details in the response. The leak includes: database name (`real_estate`), table (`inquiries`), the foreign-key constraint name and its referenced table/column (`inquiries_ibfk_1` → `properties.id`), and column width limits (`customer_phone` limited to 20 characters). Besides easing targeted attacks against the same deployment (constraint names and schema layout make blind exploitation of other issues far more reliable), the error channel also fingerprint server versions via SQLSTATE codes. The fix is trivial: log the exception server-side and return a generic message.

## PoC

- Probe 1 — nonexistent `property_id` triggers the foreign-key violation, leaking schema details:

```
POST /submit_inquiry.php HTTP/1.1
Host: 127.0.0.1:8144
Content-Type: application/x-www-form-urlencoded

property_id=99999&customer_name=ErrProbe&customer_email=probe@test.local&message=fk-probe
```

- Response (verbatim):

```
{"success":false,"message":"Database error: SQLSTATE[23000]: Integrity constraint violation: 1452 Cannot add or update a child row: a foreign key constraint fails (`real_estate`.`inquiries`, CONSTRAINT `inquiries_ibfk_1` FOREIGN KEY (`property_id`) REFERENCES `properties` (`id`) ON DELETE CASCADE)"}
```

  Leaked: database `real_estate`, table `inquiries`, constraint `inquiries_ibfk_1`, referenced `properties.id`, cascade behavior.

- Probe 2 — overlong `customer_phone` leaks the column's width restriction:

```
POST /submit_inquiry.php HTTP/1.1
Host: 127.0.0.1:8144
Content-Type: application/x-www-form-urlencoded

property_id=1&customer_name=ErrProbe2&customer_email=probe2@test.local&customer_phone=012345678901234567890123456789&message=len-probe
```

- Response (verbatim):

```
{"success":false,"message":"Database error: SQLSTATE[22001]: String data, right truncated: 1406 Data too long for column 'customer_phone' at row 1"}
```

## Payload

```
property_id=99999                                                        -> FK violation message
customer_phone=012345678901234567890123456789 (30 chars into varchar(20)) -> truncation message
```

## Evidence

- This finding is verified entirely over HTTP; the complete live request/response exchanges (both probes, curl `-i` transcripts) are preserved in `poc/F03-error-disclosure.txt`. No web-page screenshot is required — the leaked JSON above is the vulnerability's direct output.

## Suggested repair

1. **Never return driver messages to clients:** in the catch block at `submit_inquiry.php:28-30`, log `$e->getMessage()` to a server-side error log and respond with a generic string, e.g. `['success' => false, 'message' => 'Unable to submit your inquiry at this time.']`.
2. **Validate input against schema before the query:** cast `property_id` to `int` and check existence, and cap `customer_phone` at 20 characters / `customer_name` at 255 before insert.
3. **Disable verbose errors in production:** ensure `display_errors=Off` and the PDO error mode for unhandled paths does not surface stack traces.
4. **Add rate limiting/monitoring:** alert on repeated failed inserts from one client — systematic schema probing looks exactly like this.
