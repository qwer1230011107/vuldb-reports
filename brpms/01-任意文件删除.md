## Overview

- Barangay Resident Profiling and Information Management System (BRPMS, "Barangay San Fabian" build), version 1.0, allows arbitrary file deletion on the web server. The user-update handler in `/users.php` reads the profile-image filename from the client-controlled `current_image` POST field and passes it straight to `unlink()` with only an `uploads/` prefix — no basename normalization, no containment check — so a `../` traversal path deletes any file the PHP process can access, both inside and outside the web root.

## Details

- Vulnerable file: `/users.php`
- Parameter: `current_image` (POST, multipart)
- Affected version: 1.0 (current public download, 2026-11)
- Access: requires a logged-in session of the main administrator (`user_id == 1`, enforced at users.php:9). The same request is a routine form submission with **no CSRF token**, so an external attacker page can trigger the deletion against a logged-in admin without knowing any credentials.
- The vulnerable code:

```php
// users.php:98
$profile_image_name = $_POST['current_image']; // Keep old image by default
...
// users.php:105-106
if ($_POST['current_image'] != 'default.png' && file_exists('uploads/' . $_POST['current_image'])) {
    unlink('uploads/' . $_POST['current_image']);
}
```

The value comes from a hidden form field that the attacker fully controls; `file_exists()`/`unlink()` concatenate it onto `uploads/` verbatim. `../` escapes the upload directory.

## Description

- When an administrator edits a user and uploads a new profile picture, the application deletes the "old" image named by the `current_image` POST field. Because that field is client-controlled and never normalized (no `basename()`, no `realpath()` containment), any relative path such as `../canary.txt`, `../../db.php`, or an absolute-style traversal chain is accepted and unlinked. Deleting `../db.php` breaks the entire application (DB connection include); deleting framework/config files anywhere the PHP user can reach causes persistent denial of service. Combined with the missing CSRF token on this form, an unauthenticated attacker can weaponize it: lure a logged-in main admin to a hostile page, which silently submits the crafted multipart POST and deletes server-side files.

## Suggested repair

1. Never pass client-supplied filenames to `unlink()`. Keep the DB as the source of truth: read the stored `profile_image` for the user being updated and delete only that value.
2. If client input must be used, harden it: `$name = basename($_POST['current_image'])` plus a `realpath()` containment check that the resolved path is inside `uploads/`, and allow only the image extensions the app itself generates (`jpg/jpeg/png/gif` from `uniqid()` naming).
3. Add a CSRF token to all state-changing forms in `users.php` (the update and delete handlers currently accept any same-URL POST without one).
4. Least privilege: run PHP under an account that cannot write outside `uploads/` and the app directory, so a future path bug cannot reach system files.
